# 現場／辦公室待辦盤點

MetalAutoUQDwpf 的工作在兩個地方做完：辦公室（寫程式、測試、複核）和真機現場（部署、量測、驗收）。票會一路累積成「程式做完了、只差真機那一格」。這個 skill 把散在 `.scratch/` 票面、GitHub、git log 和交接文件裡的狀態收成兩張可以照著做的清單，並把**現場 agent 自己就能驗的排在最前面**。這樣使用者在現場的時間，只花在真正要人動手的那幾項上。

**範圍**：只在 MetalAutoUQDwpf 的 checkout 裡用（cwd 在 repo 根）。腳本靠它的 `.scratch/<feature>/issues/` 票格式、`.scratch/field-report-*.md` 現場回報、`.scratch/check-deployed-config.ps1`，在別的 repo 跑不出東西。

**跟 `field-handoff` 的分工**：`field-handoff` 管交接檔怎麼寫（方向、檔名、骨架、鐵律）；這支管**清單內容**：還剩哪些、真機哪幾格誰能驗、先後順序。要寫交接檔或現場提示詞時，用這支產出的 A／B／C 清單去填 `field-handoff` 的骨架。這個 repo 實際的提示詞檔名是 `.scratch/handoff-field-agent-prompt-<N>.md`（依版號遞增），不是 `field-handoff` 寫的日期檔名，沿用 repo 的寫法。

## 步驟

### 1. 先跑掃描腳本（只讀）

```bash
bash ~/.agents/skills/field-office-checklist/scripts/scan-open-work.sh
```

想指定現場 exe 的版本，就把 commit 當參數傳進去。不給參數時，腳本會從最新一份 `.scratch/field-report-*.md` 抓第一個 `1.0.0+<sha>`。

腳本吐出四段：

| 段 | 內容 | 拿來做什麼 |
| --- | --- | --- |
| 1 | 最新現場回報（和它照哪一版提示詞做）、全部的現場提示詞、field-to-office、office-end、field-visit 總表 | 下一步要讀的檔 |
| 2 | 票，已粗分（見下表） | 分類的原料 |
| 3 | 現場 exe 之後的程式 commit（`*.cs`、`*.xaml`、專案檔、`Machine/`） | 「還沒上機的改動」那張表 |
| 4 | 兩個 repo 在 GitHub 上的 open issue 與標籤 | 補進兩張清單 |

第 2 段的粗分：

| 分類 | 意思 | 通常放哪 |
| --- | --- | --- |
| `FIELD` | `ready-for-human` | 真機那張 |
| `FIELD?` | 狀態不標準（`open`、`進行中`），但票面寫著剩真機 | 讀票面確認，多半是真機 |
| `FIELD-WAIT` | 使用者決定「等現象再出現」或「先不查」 | 不排進現場工作；寫一行「現象再出現時翻紀錄」 |
| `DONE-NEW` | 基準日（現場 exe 那天）當天或之後才 `done` 的票：可能已經在現場 exe 裡，但真機多半還沒驗；也混著沒有真機那一半的（例：搬檔），讀一眼就丟 | 找它所屬功能的真機驗收票（例如 `flow-reset/06`–`22` 都歸 `flow-reset/04`）；沒有驗收票的就自成一格 |
| `ASK` | `needs-info` | 順手問使用者 |
| `OFFICE`／`BLOCKED`／`LATER` | 辦公室能做／卡前置／以後再做 | 辦公室那張 |
| `NO-STATUS`／`OTHER` | 狀態行缺或看不懂 | 讀票面判斷 |

基準日以前 `done`、票面寫著「未上真機」的舊票只報張數：它們通常已由各功能的真機驗收票涵蓋，全列會淹掉清單。

腳本只看票面 `**Status:**` 的開頭幾個字，所以只是粗分。**以票面為準、不要信舊總表**：`handoff-*-field-visit.md` 是某一天的快照，裡面打勾的、沒打勾的都可能已經過時。

### 2. 讀最新的現場脈絡

照第 1 段列出的檔，依序讀：

1. 最新的 `.scratch/field-report-*.md`：上次現場做到哪、改過哪些現場檔、量到什麼、哪幾格還是 `__`（空白就是還沒抄）。
2. 現場回報**照著做的那一版**提示詞（第 1 段會印出來）：上一版排了什麼。沒做完的格子要原樣搬進新版。比現場回報還新的提示詞是下一趟的草稿，不是上一趟做過的事；要改版就在草稿上改，不要另開一版。
3. 最新的 `.scratch/handoff-*-office-end.md` 或 `HANDOFF-*-field-to-office.md`：辦公室出貨了什麼、拍板了什麼、剩什麼。
4. `git log` 上最近幾筆 vault commit（`開發進度`、`驗證紀錄`）：常寫著「真機都還沒驗」的新改動。

先把 `DONE-NEW` 歸到它所屬功能的驗收票（同一個資料夾裡標題有「驗收／field／acceptance」的那張），歸不進去的才當成獨立一格。歸完之後，`FIELD`＋`FIELD?`＋歸不進去的 `DONE-NEW` 加起來多於 10 張，就派唯讀 `Explore` agent 分頭讀，每個 agent 約 15 張、最多 3 個。下一步要等它們的結果，所以用**前景**（`run_in_background: false`），不要開背景再自己等。給它們的 prompt 骨架：

```text
唯讀。逐張讀下面這些票的 Status、「剩什麼／現場要做的／驗收」段，每張回一行：
<票路徑> | 剩哪一格（一句） | 層：A（只讀紀錄、診斷匯出、畫面、只讀 SDO）／B（要人按會動或會改現場狀態的東西、或要人看實物）／C（要教點、要 Auto 跑、要樣品或外部設備） | 有沒有辦公室那一半（例：artifact republish） | 有沒有被別張票或後端 issue 擋住
票：<清單>
```

lead 只拿結論，不自己把 40 張全讀一遍。

### 3. 分類

#### 真機那張：依「誰能驗」分三層

這一層是這個 skill 的重點。依據是現場鐵律：**agent 不下會動機構的命令**。軸、磁浮、氣缸、起子、DIO 輸出、切操作模式、上下伺服、斷開／連上匯流排，都只能由使用者本人按。所以判斷每一格時，要問的是「驗這一格，需不需要有人按會動的東西，或用眼睛看實物」。

| 層 | 判準 | 典型例子 |
| --- | --- | --- |
| **A：agent 自己驗** | 只靠讀紀錄（`uqd-logs/*.jsonl`、`link-events`）、連線頁「匯出診斷」、遙測、UIA 讀畫面與截圖、只讀的 `read_sdo`、ssh 讀後端設定與 `MANIFEST`，或按「匯出診斷」這類不動機構的鈕 | 後端 WKC 數字、connect 紀錄欄位、某顆鈕灰不灰、新畫面長相、幀大小、服務啟動參數 |
| **B：使用者按、agent 抄** | 要有人按會動的命令，或要人看實物（目視氣缸、做記號轉一圈），但不需要先教點、也不需要整台 Auto 跑起來 | 停止與流程重置各格、套用操作模式、單軸停、入料軸量行程 |
| **C：要教點、要 Auto、要外部前置** | 要先教位置、整台 Auto 跑一段（N 顆、節拍）、要樣品，或要 KUKA 控制器、相機等外部條件 | 三站平行教點、跑 100 顆量節拍、Data Matrix 樣品、APP1 安裝 |

分層時注意：

- **同一張票可以拆在兩層**。例如 `csp-switch-keeps-op/02`：診斷三格是 A，「套用」按下去的結果是 B。拆開寫，A 那一半就能先收。
- **開／關 WPF HMI 算 B**：開程式就是連上匯流排、註冊軸、寫驅動器 SDO，跟按「連上匯流排」是同一件事。2026-10-12 的複核就抓到一版把「重開程式看第一次連線」排進 A 層。
- **不動機構、但會改現場狀態的鈕也算 B**：「存成預設」（寫現場設定檔）、切換 profile（整份覆蓋現場檔）、「收掉編排角色」、「套用」操作模式（就算預期會被拒）。判準是「按完現場有沒有東西跟按之前不一樣」；只有「匯出診斷」這類純讀的鈕才是 A。
- **被後端 bug 擋住的格子要註明**：例如 `csp-switch-keeps-op/01`、`02` 的結果取決於後端 #127 修了沒。照排，但在格子裡寫「後端 #N 還沒修，被擋是預期之一」，現場 agent 才不會當成新問題。
- **看到「手動送一支 `read_sdo`」先回票面確認**：票要的常常是就緒序列**自動送**的那幾支回覆（看 `link-events`），不是叫人另外送。
- **畫面上的數字照畫面格式寫**：先去讀格式化那一行再寫（例：`MetalAutoUQD.AppModel/ViewModels/CommissioningViewModel.RebuildParams.cs:543` 一萬以上用 `#,0`，所以畫面是 `1,223,339`），不要寫算出來的 `1,223,338.7`，否則現場 agent 會判成不過。
- **分清 exe 旁的 `uqd.json` 和 `profiles\`**：硬體切換頁與 profile 讀的是 `profiles\`（建置時由 `Machine/uqd.json` 複製），不是現場手改過的那一份；切換 profile 會整份覆蓋現場檔。
- **上一次現場已經抄到的值**（例如 field-report 裡寫著 17:29 看到 `slaves_not_in_op:[]`），標成「寫回就能收」放在 A 層，不要再叫人去量。
- **第 3 段每一筆 commit 都要有落點**。對不上任何票的，就在開工前那張表直接寫「驗哪一格」。
- **後端 GitHub issue** 標 `ready-for-human` 的，只挑跟這次上機有關的（剛部署的、現場票提到的），其餘寫成「後端 #N–#M 那一串」，不要逐張列。

#### 辦公室那張

| 來源 | 放哪 |
| --- | --- |
| `OFFICE`（`ready-for-agent`、`needs-triage`、`進行中`） | 辦公室能直接做；`needs-triage` 要先問使用者要不要做 |
| `BLOCKED` | 寫出卡在哪個前置條件 |
| `LATER`（`以後再做`） | 只寫張數與一行主題，除非使用者問 |
| GitHub `needs-triage`（後端常有） | 辦公室要先對帳：是不是已經做掉了（`.scratch/backlog-triage-*.md` 有前例） |
| 現場回報「下一步（要辦公室決定的）」 | 逐條搬過來 |
| `FIELD` 票裡的辦公室那一半（例：「剩 artifact republish」） | 兩張都列：真機那張放量測，辦公室這張放 republish；先查是不是已經做了 |
| `NO-STATUS`／`OTHER` | 讀票面判斷，修好狀態行 |

#### 另外兩類

- **`ASK`（`needs-info`）**：列成「順手問使用者」，一張一行講要問什麼。
- **可能已經過時的票**：票面要驗的功能已經拿掉了（例如示範模式：2026-10-09 拍板拿掉、2026-10-10 落地），就列在「要你決定」，建議結成 wontfix。**不要自己改票面狀態**。

### 4. 輸出

#### 在對話裡（預設）

照專案的輸出風格：結論先行、條列、繁體中文、狀態與參數用原名加反引號。骨架：

```text
<一句話：明天建議怎麼排、A 層幾項>

**要你決定**
- （過時的票、現場檔要不要改、哪一份 profile……）

## 開工前（1、2 agent 自己做；3 請使用者開程式）
1. 重建：現場 exe 停在 <sha>，之後有 N 筆程式改動沒上機（一行列名）
2. 開程式前跑 .scratch/check-deployed-config.ps1 驗現場 uqd.json：FellBack=False
3. 請使用者開程式，對 app-events 的 start version

## A. agent 自己能驗（表：# | 驗什麼 | 去哪看 | 票）
## B. 你按、agent 抄（依優先序編號）
## C. 要教點或要 Auto（依主題分組，一組一行）
## 辦公室（有才寫）
## 順手問你（needs-info）
```

開工前那幾步永遠排最前：現場檔設定錯了，後面全部會量錯。

B 層的排序，前一條比後一條優先：

1. **會擋住後面格子的先做**：例如入料軸沒量行程與軟極限，就教不了取放點。
2. **涵蓋票最多的那一批**：一次驗收能收掉最多 `DONE-NEW` 的排前面（2026-10-12 是流程重置那 12 格，對到 18 張票）。
3. **最新出貨的**：同分時，越新的越可能有沒被假庫抓到的問題。

#### 寫成交接提示詞（使用者要求時）

寫成 `.scratch/handoff-field-agent-prompt-<N+1>.md`，形狀照最新一版：

1. 開頭一段：前一版是哪份、做到哪、這一版多了什麼。
2. 「貼給現場 agent」code block：角色、先讀哪些檔、環境（路徑、後端 build_id）、鐵律、順序。
3. `P0 開工前`：重建指令（`-c Release -p:Platform=x64` 兩個都帶）、載入器驗設定檔（下面那支腳本）、對版本、要先問使用者的現場檔改動（含備份檔名）。
   ```bash
   pwsh -File .scratch\check-deployed-config.ps1
   ```
   它不開程式，直接呼叫開機用的 `DeployedConfig.Resolve`，印出 `FellBack` 與後端位址；退回時 exit 1 並印出原因。要 PowerShell 7.6 以上（.NET 10）。
4. A／B／C 三層，每格寫：怎麼做、要看到什麼（數字或原句）、票。
5. 順手問使用者、已知不用驗、回報骨架（`.scratch/field-report-<日期>.md`）、收工整理。

上一版沒做完的格子要原樣搬進來，並註明「上一版沒做」。決定不排的，列在「這版不排的」並寫原因，不要無聲拿掉。

寫完派一個唯讀 agent 逐條核對事實：commit 內容、票路徑與狀態、引用現場回報的數字、A 層有沒有混進會動機構的動作、上一版有沒有被無聲拿掉的格子。改完再交給使用者（本 repo 的規矩：每一份改動都要獨立複核）。

## 為什麼要這樣排

- **A 層先做**：使用者在現場最稀缺的是時間和注意力。A 層可以在他教點或處理別的事時平行跑，而且常常一份診斷匯出就能同時收掉好幾張票。
- **開工前驗設定檔**：2026-10-12 新版程式加了必填鍵、沒有遷移，現場 `uqd.json` 缺一格，整台就退回內建模擬設定。畫面只看得到「連不上 127.0.0.1」，查了一個多小時。開程式前跑 `.scratch/check-deployed-config.ps1`，`FellBack : False` 才往下走。
- **以票面為準**：總表與交接檔是快照。2026-10-12 的總表就把早已 `done` 的 `partial-ring-connect/08`、`dio-config/16` 列成待辦。

## 不做的事

- 不改票面 `**Status:**`、不關 GitHub issue、不 push。這個 skill 只盤點；結票、改標籤要使用者點頭。
- 不碰 vault（`WpfAutoUQDobsidian/`）。要寫回 vault 是另一件事，照 `CLAUDE.md` 用 obsidian skill。
- 不猜現場數字。上一次沒抄到的就寫「還沒抄」。
