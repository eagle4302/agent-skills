# 流暢度量測定義

> 預設門檻的單一來源是 `SKILL.md` 的「Default Metrics and Thresholds」表。
> 這份只寫「怎麼算、怎麼取樣、怎麼報」。

## 1. 流程指標

| 指標 | 定義 | 計算 |
|---|---|---|
| 任務成功率 | 完成任務的人數比例 | 成功人數 ÷ 總人數 |
| 任務步數 | 有效操作次數（不含誤點與說明性點擊） | 從開始到成功的操作計數 |
| 規劃步數差 | 實際步數 − 規劃最短路徑 | 正數代表繞路 |
| 回頭次數 | 回到已離開畫面的次數 | 計數 |
| 誤點率 | 點到非目標區域的次數比例 | 誤點次數 ÷ 總點擊 |
| 任務時間 | 從開始到成功的秒數；失敗記上限（例 300s） | 中位數與 p95 |
| 求助次數 | 主動問主持人或查說明的次數 | 計數 |
| 狀態辨識正確率 | 任務後能正確說出目前狀態的比例 | 正確人數 ÷ 總人數 |
| 錯誤恢復步數 | 從錯誤發生回到原任務的步數 | 計數；>2 視為不合格 |

## 2. 手感指標

| 指標 | 定義 | 取樣 |
|---|---|---|
| 輸入到回饋延遲 | 輸入事件 timestamp → 第一個可見回饋 timestamp | 每次互動 ≥ 30 次，報 median 與 p95 |
| 動畫時長偏差 | \|實測 − 規格\| ÷ 規格 | 每種動畫 ≥ 10 次 |
| 幀時間 | 連續渲染間隔（ms）；統計 p50、p95、max | 每段 ≥ 10 秒 |
| Jank 次數 | 幀時間 > 50ms 的次數 | 每段 ≥ 10 秒 |
| UI heartbeat jitter | 16ms 心跳計時的實際間隔與理想值偏差 | 30 秒以上 |
| 焦點順序錯誤 | Tab 順序與視覺順序不一致的次數 | 完整 Tab 一輪 |
| 觸控命中 | 點在目標中心與邊緣 4 點是否都觸發 | 每個目標 5 次 |

## 3. 韌性指標

| 指標 | 定義 |
|---|---|
| 邊界案例通過率 | 通過的邊界案例數 ÷ 計畫數 |
| 崩潰與卡死 | 腳本化操作中的 crash／freeze 次數（目標 0） |
| 記憶體成長 | 30 分鐘 soak 前後 RSS 差值（專案定義上限） |
| 錯誤恢復 | 錯誤後回到任務的步數與成功率 |
| 重複送出 | 快速連點後實際產生的請求數（應為 1） |
| 版面破損 | 極端資料下重疊、裁切、值錯誤的數量（目標 0） |

## 4. 取樣與環境

- 每個互動量測 ≥ 30 次；先預熱 1 次，排除前 3 次。
- 受測者 2–5 位；每位 5–8 個任務；單場 30–45 分鐘。
- 固定環境：build／commit、解析度、DPI／縮放、字型、動畫開關、資料 fixture、網路條件、電源模式。
- 同一輪內不要換 build 或機器；換了就標成新 baseline。
- Debug build 的數字只能標「參考」，不能拿來判定通過。

## 5. 報表規則

- 每個數字都要附 n、median、p95、環境、build。
- 不要只報平均數；平均數會掩蓋長尾。
- 單次量測不算結果。
- 與門檻比較時註明是「預設門檻」還是「專案自訂門檻」，並寫出理由。
- 未達門檻但使用者感受不到時，仍要記錄，交由使用者決定是否接受。

## 6. 計算範例

- 50 次點擊延遲：median 42ms、p95 88ms、max 140ms → 門檻 ≤100ms，p95 通過，max 需註記。
- 10 秒渲染：120 幀，p95 16ms、max 62ms、jank 1 次 → 門檻 p95 ≤16.7ms 通過，但 jank 需檢視是否在資料刷新瞬間。
- 8 位受測者、5 個任務：成功 39／40，1 位在「確認警報」迷路 → 成功率 97.5%，列 Major。

## 7. 常見錯誤

- 只量一次就下結論。
- 用平均數取代 p95。
- 在 Debug build、動畫開啟、不同 DPI 的環境下量。
- 把瀏覽器原型的延遲當成原生 app 的延遲。
- 把「使用者說喜歡」當成流暢度證據。
- 門檻看到結果後才改。
